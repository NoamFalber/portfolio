Cave Map Workshop

I rebuilt my Unity cave editor as a tool that works at runtime. Draw and validate a layered map, generate the 3D cave and NavMesh, then jump straight into the project’s existing spell-combat loop. The same core rules drive the desktop and WebGPU versions.

01 · The problem

The map tool worked. Unity’s editor was the part that could not ship.

The original map painter was an approximately 5,000-line EditorWindow built around editor Undo, AssetDatabase, saved meshes, scene changes, and direct project references. I wanted the full tool in a playable build, not a smaller imitation of it.

I kept the mature tile rules and procedural generator, then replaced the editor-only shell with runtime systems that desktop and web can share.

  • Portable mapsVersioned JSON uses stable tile and catalog IDs.
  • Runtime historyEvery stroke, fill, resize, and setting change is undoable.
  • Shared validationThe same rules protect authoring and the final build.
  • Owned resourcesGenerated meshes, materials, and NavMesh data are cleaned up safely.

02 · Editor and authoring

The rules live under the canvas, not inside the UI.

Brush, Rectangle, Region Fill, erase, resize, and marker settings all go through one transaction service and one set of topology rules. That keeps the tool predictable even when several kinds of data share one cell.

  • Three layersCave shape, gameplay markers, and Guide Lamps can work together.
  • Safe editingA drag is one undo step; fast strokes fill skipped pointer cells.
  • Protected topologyOne start, one connected finish, attached pits, and stable encounter groups.
  • Clear validationErrors block generation. Warnings explain risk without stopping a valid map.

64 × 64, one UI mesh. The canvas batches 4,096 cells, symbols, outlines, previews, hover states, and validation feedback instead of creating one GameObject per cell.

03 · Runtime generation

Build & Play makes the level the game actually uses.

  1. ValidateFreeze and recheck the map.
  2. ShapeBuild floors, curved walls, roof, pits, and seeded detail.
  3. PlaceAdd spawn, encounters, finish, pools, wind, and lamps.
  4. CollideKeep detailed visuals and player-safe collision separate.
  5. NavigateBake ground and flying NavMesh data.
  6. PlayBind the systems and enter first-person combat.

Generation yields between expensive stages so the browser can show honest progress. Returning to the editor disposes the generated lifetime before the next build, without touching shared project assets.

04 · WebGPU delivery

I designed the browser version around Unity 6 WebGPU from the start.

The project has a dedicated renderer, quality path, browser preflight, and release validator. A production build is rejected unless WebGPU is the only graphics API.

  • Useful preflightHTTPS, desktop input, WebGPU, and a high-performance adapter are checked before Unity downloads.
  • No quiet fallbackAn unsupported setup gets a clear message instead of a hidden WebGL switch.
  • Browser budgetsThe heap can grow from 256 to 2,048 MiB; device pixel ratio is capped at 1.5.
  • Correct deliveryHashed Brotli files are served with the MIME and encoding headers Unity needs.
