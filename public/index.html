Surreal Landscape Prototype

This started as a rolling-ball meadow and grew into a rendering-systems study. The terrain streams around the player, grass is culled on the GPU, trails recover over time, and the clouds are raymarched. I keep separate settings for desktop and WebGPU.

01 · Bounded world

The world repeats around a finite moving window.

One deterministic height function places the terrain, collision, grass, player, and wandering balls on the same surface. Small local buffers move with the player, while the generated world stays consistent.

  • TerrainAbout 130 active LOD tiles; a representative view submits roughly 50–55.
  • CollisionOne local double-buffered patch replaces world-sized MeshColliders.
  • EncountersEleven prewarmed balls keep ten active without normal Instantiate or Destroy.
  • Frame budgetThe world can repeat indefinitely while memory, objects, and per-frame work stay fixed.

02 · Grass and terrain

The grass is culled on the GPU and drawn in three LOD passes.

Grass candidates come from world-aligned cells. A compute pass removes hidden blades, picks an LOD, packs the interaction data, and writes the remaining blades to three append buffers.

  • Stable identity8 m distribution cells group into 16 m chunks with an 80-chunk cache.
  • Three LODsNear, middle, and far blades use 30, 15, and 3 generated vertices.
  • WindFour pressure fields bend each rooted blade arc.
  • Distant fieldA virtual-canopy material continues the grass after the geometry fades.

160 candidates per m² at full density. The CPU manages the cache and dispatches. Compute shaders handle culling, deformation, lighting, and the three draws.

03 · Contact and trails

The ball leaves trails that recover after one minute.

During culling, a swept-sphere test bends nearby blades. Touched cells are saved in sparse pages so the trail keeps its direction, age, and recovery after the ball moves on.

  • Instant contactLive bend data reuses spare bits in the existing blade payload.
  • Sparse memory8 m CPU pages are created only where the player or an encounter touches grass.
  • Fixed GPU atlas512 texture-array slices hold an 8 MB persistent field.
  • Exact recoveryGrass stays pressed for 57.8 seconds, then returns over 2.2 seconds.

The WebGPU profile uploads at most four 16 KiB pages per frame, starting with the pages nearest the player. Wandering balls use the same trail system.

04 · Clouds and lighting

Up to 64 raymarched clouds share one draw.

Each cloud is a small instance record. One procedural draw raymarches the volumes, giving them parallax and internal depth, while a compute field adds their shadows to the terrain.

  • Compact fieldUp to 64 clouds fit in one 3,072-byte instance buffer.
  • Bounded raymarchNear and far clouds use 32 and 26 steps with early exit.
  • Shared shadeA 256 × 256 compute field shades grass, terrain, balls, and meadow VFX.
  • LightingThe sky, atmosphere, clouds, and surfaces all use the same sun.

A cloud that vanished at the centre of the screen came from a signed Vulkan projection error. Correcting the proxy coordinate space fixed it.

05 · WebGPU product

The browser build has its own settings and benchmark run.

WebGPU High keeps the grass, trails, encounters, and volumetric clouds, but uses browser-specific scheduling, memory limits, warmup, and build settings.

  • Profile guardThe web setup hashes the Desktop High assets and fails if it changes them.
  • WarmupThe preparation screen runs the production scene before play begins.
  • Frame budgetsGrass, collision, trails, particles, clouds, and memory each have web limits.
  • Benchmark harnessNode and Playwright record workloads, rAF, memory, errors, and build manifests.

The stripped production output was 19,408,640 bytes before filesystem overhead. Accepted runs held the Wasm heap at exactly 256 MiB.

Cave Map Workshop

The original cave map tool only ran in Unity’s editor. I moved it into runtime so I could draw and validate a map in the build, generate the 3D cave and NavMesh, and start a combat run without leaving the game. Desktop and WebGPU use the same map rules.

01 · The problem

Moving a 5,000-line EditorWindow into the game.

The original map painter was a roughly 5,000-line EditorWindow tied to editor Undo, AssetDatabase, saved meshes, scene changes, and direct project references. Those APIs are not available in a player build.

I kept the existing tile rules and procedural generator, then wrote a runtime shell that works on desktop and the web.

  • Map formatVersioned JSON uses stable tile and catalog IDs.
  • UndoEvery stroke, fill, resize, and setting change can be reversed.
  • ValidationThe editor and the build run the same checks.
  • CleanupGenerated meshes, materials, and NavMesh data are released between builds.

02 · Editor and authoring

One set of rules handles every editing tool.

Brush, Rectangle, Region Fill, erase, resize, and marker settings all go through one transaction service and the same topology checks. Several kinds of data can share a cell without each tool needing its own rules.

  • Three layersCave shape, gameplay markers, and Guide Lamps can work together.
  • EditingA drag is one undo step; fast strokes fill skipped pointer cells.
  • TopologyOne start, one connected finish, attached pits, and stable encounter groups.
  • MessagesErrors block generation. Warnings stay visible without stopping a valid map.

64 × 64, one UI mesh. A single mesh batches all 4,096 cells along with their symbols, outlines, previews, hover states, and validation feedback.

03 · Runtime generation

Build & Play turns the map into a playable level.

  1. ValidateFreeze and recheck the map.
  2. ShapeBuild floors, curved walls, roof, pits, and seeded detail.
  3. PlaceAdd spawn, encounters, finish, pools, wind, and lamps.
  4. CollideKeep detailed visuals and player-safe collision separate.
  5. NavigateBake ground and flying NavMesh data.
  6. PlayBind the systems and enter first-person combat.

Each expensive stage yields so the browser can update the progress screen. Before the next build, the tool clears the generated meshes, materials, and NavMesh data while leaving shared project assets alone.

04 · WebGPU delivery

The WebGPU build has a separate renderer and release checks.

The browser profile has its own renderer, quality settings, preflight page, and release validator. The build is rejected unless WebGPU is its only graphics API.

  • PreflightHTTPS, desktop input, WebGPU, and a high-performance adapter are checked before Unity downloads.
  • WebGPU onlyUnsupported setups get an error message; the build does not switch to WebGL.
  • MemoryThe heap can grow from 256 to 2,048 MiB; device pixel ratio is capped at 1.5.
  • DeliveryHashed Brotli files use the MIME and encoding headers required by Unity.
