Surreal Landscape Prototype

A quiet rolling-ball meadow where movement reveals the rendering work: grass bends, trails remain, clouds shade the hills, and wandering forms cross the horizon. I built the gameplay and visual systems together so every effect responds to the same world.

01 · World architecture

The world feels endless because every system knows its limit.

I built the landscape from deterministic world data and small moving working sets. The player can travel in any direction while terrain, collision, vegetation, and encounters reuse a controlled amount of memory and work.

  • One surfaceRendering, collision, grass, and wandering actors sample the same terrain definition.
  • StreamingOnly the useful area around the player stays detailed and physically active.
  • ContinuityOld coverage remains until its replacement is ready, avoiding holes during fast travel.
  • OwnershipTiles, actors, buffers, and collision all have explicit reusable budgets.

02 · Rendering handoff

One grass system carries the image from individual blades to the horizon.

Dense nearby blades and distant terrain are different representations of the same meadow. I made them share placement, lighting, wind, trails, and atmosphere so the change in geometry does not reveal the edge of the system.

  • GPU selectionCompute work rejects hidden grass and assigns the useful geometry level before drawing.
  • Three draw pathsClose, middle, and distant blades spend detail where it changes the image.
  • Physical windPressure fields change blade posture and normals instead of painting motion over the color.
  • Virtual canopyThe terrain continues the same material response after real blades fade.

The visible grass ring disappeared only after I stopped treating the terrain as unrelated ground and made it the far representation of the same canopy.

03 · World interaction

Movement leaves a physical memory in the landscape.

The ball bends grass at first contact, even during fast movement, then leaves a directional trail that gradually stands back up. Only touched areas persist, so the effect can outlive the camera without allocating an entire world-sized texture.

  • Immediate responseA swept contact test closes the visual gap before persistent data reaches the GPU.
  • Sparse historyMemory exists only for grass the player or a wandering ball has touched.
  • Dimensional resultPressed blades change shape, direction, normals, and distant relief—not just color.
  • RecoveryOne timed envelope restores geometry, lighting, wind authority, and memory ownership.

A bounded, fair upload schedule keeps the nearest contact responsive without allowing trail updates to take over a browser frame.

04 · Visual cohesion

The sky is part of the world system, not a backdrop.

I replaced flat cloud cards with camera-independent volumes and connected their light and shadows to the same sun used by the terrain, grass, atmosphere, balls, and meadow effects.

  • Real volumeRaymarched forms keep their shape and parallax as the camera moves around them.
  • One submissionA compact instance set renders the full cloud field through one procedural draw.
  • Shared shadowsOne GPU-generated field moves cloud shade across every world material.
  • One light sourceWarm highlights, cool shade, sky, and atmosphere agree from any view.

A cloud that vanished only at the centre of a gameplay orbit turned out to be a signed projection mismatch—not a density or visual-tuning problem.

05 · Browser product

The WebGPU release keeps the project’s reason for existing.

Moving this GPU-heavy scene into a browser exposed a different set of costs: single-threaded managed work, first-use pipelines, memory growth, presentation timing, and higher submission overhead. I built a separate production profile around those constraints instead of stripping out the defining visuals.

  • Separate profilesDesktop quality stays protected while the browser owns its renderer, pacing, memory, and schedules.
  • Prepared first useThe real scene warms its shaders, buffers, terrain, collision, and pools before control begins.
  • Bounded workStreaming, uploads, collision, particles, and diagnostics each have explicit release behavior.
  • QualificationAn automated browser harness measures workload, cadence, memory, errors, and repeatable scenarios.

I kept the native cloud path after it met the stress target; a lower-resolution reconstruction would have added ghosting risk without solving a measured problem.

Cave Map Workshop

01 · Product migration

The useful rules were trapped inside a tool that could never ship.

The mature map painter was a roughly 5,000-line Unity editor window. Its undo, asset saving, scene mutation, generated meshes, and direct project references all depended on development-only APIs.

I kept the proven rules and generator as the authority, then rebuilt everything around them for runtime use.

  • Portable documentMaps store stable tile, theme, and enemy identities instead of Unity object references.
  • Runtime historyGestures and settings become bounded, reversible transactions.
  • One rule setEditing, validation, and generation agree on what makes a legal map.
  • Explicit lifetimeGenerated geometry, materials, and navigation are owned and released before rebuilding.

02 · Authoring experience

The interface explains the rules while the player is building.

Cave shape, gameplay markers, and wall-mounted functions can share a cell, but the user should not need to think like the data model. The canvas makes active tools, topology, legal placement, warnings, and build readiness visible at the point of editing.

  • Layered meaningCave shape, gameplay objects, and wall functions remain independently editable.
  • Reliable gesturesA fast drag fills gaps and becomes one understandable undo step.
  • Topology protectionUnique starts, connected finishes, attached pits, and encounter groups survive every tool.
  • Actionable feedbackErrors point to affected cells; warnings inform without blocking a playable map.

64 × 64, one UI mesh. The canvas batches 4,096 cells and their symbols, outlines, previews, and feedback instead of maintaining one interface object per cell.

03 · From plan to play

One action carries authored intent into the real game.

  1. ValidateFreeze the document and confirm the cave is ready.
  2. ShapeBuild floors, curved walls, roof, pits, and repeatable seeded detail.
  3. PlaceAdd the player start, enemies, finish, pools, wind, and lamps.
  4. CollideBuild simpler, player-safe collision separately from the detailed visuals.
  5. NavigateBuild walkable routes for ground and flying enemies using NavMesh.
  6. PlayConnect the combat systems and enter the finished cave.

The build runs in measured stages so the browser can keep reporting honest progress. The result is the existing combat loop—not a disconnected preview—with reset, enemies, pickups, hazards, completion, and return to edit.

04 · Browser delivery

The browser build is treated as a product configuration.

Runtime generation, pointer lock, persistent documents, memory growth, compressed Unity files, and GPU support all behave differently in a browser. The WebGPU profile owns those constraints explicitly and refuses to ship in an unintended fallback mode.

  • Capability gateSecure context, desktop input, WebGPU, and a suitable adapter are checked before the game downloads.
  • Honest supportUnsupported setups get a clear stop instead of a silent graphics downgrade.
  • Browser lifecycleFocus, pointer lock, pause UI, storage sync, and rebuild cleanup have explicit owners.
  • Delivery contractThe release validates renderer settings, memory, caching, Brotli headers, and required assets before building.
