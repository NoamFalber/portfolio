Surreal Landscape Prototype

This started as a rolling-ball meadow and became a study in making a large, reactive world run efficiently. The terrain follows the player, the grass bends and keeps fading trails, and volumetric clouds cast shadows. GPU culling and browser-specific settings keep the same core experience working on desktop and WebGPU.

01 · Bounded world

A small moving window creates the feeling of an endless world.

Instead of building one enormous map, I reuse a fixed set of nearby terrain and collision pieces as the player moves. One shared height function keeps the ground, grass, player, and wandering balls on the same surface, so the recycled pieces join without changing the world.

  • TerrainAbout 130 detail-scaled tiles stay active; a typical view draws roughly 50–55.
  • CollisionTwo local physics patches trade places around the player instead of covering the entire world.
  • EncountersEleven preloaded balls keep ten active without repeatedly creating and destroying objects.
  • Fixed costThe scenery can continue indefinitely while memory, object count, and per-frame work stay bounded.

02 · Grass and terrain

The GPU decides which blades to draw and how detailed they need to be.

The world is divided into stable cells, so the same grass returns in the same place. A compute shader removes off-screen blades, assigns one of three detail levels, adds wind and trail data, then sends the visible grass to three draw buffers.

  • Stable placement8 m cells group into 16 m chunks; only 80 nearby chunks stay cached.
  • Three detail levelsNear, middle, and far blades use 30, 15, and 3 generated vertices.
  • WindFour overlapping wind waves bend every blade from its root.
  • Distant fieldA matching terrain material continues the grassy look after real blade geometry fades.

160 possible blades per m² at full density. The CPU keeps nearby cells ready; compute shaders choose, bend, light, and draw only the grass needed for the current view.

03 · Contact and trails

The ball leaves trails that recover after one minute.

Grass under the rolling ball bends immediately. To keep that path visible after the ball moves on, the system stores only the touched 8 m cells, together with their bend direction and age.

  • Instant contactA swept-sphere check catches the ball between frames, even when it moves quickly.
  • Sparse memoryTrail pages exist only where the player or a wandering ball has touched grass.
  • Fixed GPU storage512 texture-array slices provide a bounded 8 MiB field for persistent trails.
  • Exact recoveryGrass stays pressed for 57.8 seconds, then returns over 2.2 seconds.

The WebGPU profile uploads no more than four 16 KiB trail pages per frame, nearest first, so trail updates cannot take over the frame. Wandering balls use the same system.

04 · Clouds and lighting

Up to 64 volumetric clouds are rendered together in one draw.

The clouds have real depth rather than being flat sky cards. One shader samples through every cloud volume, while a separate compute-generated field places their moving shadows on the landscape.

  • Compact dataUp to 64 clouds fit in one 3,072-byte GPU instance buffer.
  • Bounded samplingNear and far clouds use at most 32 and 26 raymarch steps, with an early exit when no more detail is visible.
  • Shared shadowsA 256 × 256 GPU-generated shadow field shades the grass, terrain, balls, and meadow effects.
  • LightingThe sky, atmosphere, clouds, and surfaces all use the same sun.

One difficult bug made a cloud disappear at the centre of the screen. I traced it to a signed Vulkan projection error and fixed the cloud proxy’s coordinate conversion.

05 · WebGPU product

The browser build keeps the visual systems, but runs on its own budgets.

WebGPU High keeps the grass, trails, wandering encounters, and volumetric clouds. Browser-specific scheduling, memory limits, warmup, and build settings keep those systems practical in a tab.

  • Desktop guardA build check fingerprints the Desktop High assets and stops if browser work changes them.
  • WarmupA preparation screen runs the real scene once before handing control to the player.
  • Frame budgetsGrass, collision, trails, particles, clouds, and memory each have explicit browser limits.
  • Automated benchmarkNode and Playwright record frame timing, display cadence, memory, errors, screenshots, and build data.

The new build report lists a 19,409,361-byte payload (18.5 MiB). Accepted benchmark runs kept the WebAssembly memory allocation fixed at 256 MiB.

Cave Map Workshop

The original cave-building tool only worked inside Unity’s editor. I rebuilt the workflow so it runs in the game: draw a 2D cave, get clear validation, generate the 3D geometry and enemy navigation, then play it immediately. Desktop and WebGPU use the same map data and rules.

01 · The problem

Rebuilding a 5,000-line Unity editor tool for players and browsers.

The original map painter was a roughly 5,000-line EditorWindow that only worked inside Unity’s development environment. It depended on editor Undo, AssetDatabase, saved meshes, scene changes, and direct project references—systems that cannot ship in a playable build.

I kept the proven tile rules and cave generator, then built a new in-game interface, document format, validation layer, and cleanup system that owns every generated resource.

  • Portable mapsVersioned JSON uses stable names for tiles, themes, and enemies instead of Unity object references.
  • UndoEvery stroke, fill, resize, and setting change can be reversed as one clear action.
  • Shared validationThe Unity editor and playable build run the same map checks.
  • CleanupGenerated meshes, materials, and navigation data are explicitly released before rebuilding.

02 · Editor and authoring

Every brush and setting uses one shared rule system.

Brush, Rectangle, Region Fill, erase, resize, and marker settings all pass through one transaction service and the same cave-layout checks. Base geometry, gameplay markers, and functional overlays can share a cell without each tool inventing separate behavior.

  • Three layersCave shape, gameplay markers, and wall-mounted Guide Lamps can work together.
  • EditingA drag is one undo step; fast strokes fill skipped pointer cells.
  • Layout rulesOne player start, one connected finish, attached pits, and stable enemy groups.
  • MessagesErrors block generation. Warnings stay visible without stopping a valid map.

64 × 64, one UI mesh. Rather than create 4,096 separate interface objects, one mesh batches every cell, symbol, outline, preview, hover state, and validation message.

03 · Runtime generation

Build & Play turns the 2D plan into a complete combat level.

  1. ValidateFreeze the document and confirm the cave is ready.
  2. ShapeBuild floors, curved walls, roof, pits, and repeatable seeded detail.
  3. PlaceAdd the player start, enemies, finish, pools, wind, and lamps.
  4. CollideBuild simpler, player-safe collision separately from the detailed visuals.
  5. NavigateBuild walkable routes for ground and flying enemies using NavMesh.
  6. PlayConnect the combat systems and enter the finished cave.

Expensive stages pause between groups of work so the browser can update its progress screen instead of appearing frozen. Before rebuilding, the tool clears everything it generated while leaving shared project assets untouched.

04 · WebGPU delivery

The browser version has a dedicated renderer and a release gate.

The browser profile has its own renderer, quality settings, startup check, and release validator. A production build is rejected unless WebGPU is the only graphics API, so an unsupported machine gets a clear message instead of a silent visual downgrade.

  • Startup checkHTTPS, desktop input, WebGPU, and a high-performance graphics adapter are checked before Unity downloads.
  • WebGPU onlyUnsupported setups get an error message; the build does not switch to WebGL.
  • MemoryWebAssembly memory can grow from 256 to 2,048 MiB; render resolution is capped at 1.5× device pixel ratio.
  • DeliveryCache-safe Brotli files are served with the content types and compression headers Unity expects.
