Surreal Landscape Prototype

Surreal Landscape is a solo project that combines GPU rendering, world streaming, interaction, and gameplay in one continuously moving scene. I carried the complete visual feature set into WebGPU, built a dedicated browser profile, and qualified the production release with repeatable tests.

01 · Bounded world streaming

Fixed budgets support continuous travel in every direction.

I generate the landscape from deterministic world coordinates and move limited working sets with the player. Terrain meshes, collision tiles, grass data, and wandering encounters reuse fixed pools instead of accumulating as the player travels.

  • Shared height fieldTerrain, collision, grass, and wandering actors sample the same surface definition.
  • Active areaOnly the required range around the player stays detailed and physically active.
  • Streaming handoffExisting coverage stays active until replacement tiles are ready, preventing gaps during fast travel.
  • Fixed poolsTiles, actors, buffers, and collision reuse defined capacities.

02 · Grass rendering

Three GPU-driven detail levels render dense grass from the player to the horizon.

A compute shader culls hidden blades and assigns visible grass to close, middle, or distant geometry. Beyond the blade range, the terrain shader continues the same distribution, lighting, wind, trails, and atmosphere to remove the visible edge around the rendered grass.

  • Compute cullingThe GPU rejects hidden blades and assigns the required geometry level before drawing.
  • Three indirect drawsClose, middle, and distant blades use separate geometry budgets.
  • Blade windPressure fields change blade position, posture, and normals rather than shifting color alone.
  • Terrain handoffThe ground shader continues the grass response after full blade geometry ends.

The terrain handoff removed the visible grass ring without extending full blade geometry into the distance.

03 · Persistent interaction

Fast movement produces continuous grass trails that recover over time.

Swept sphere contact bends blades immediately and fills gaps between movement samples. Sparse CPU pages retain only touched areas, then upload directional trail data to a fixed 8 MB GPU atlas so trails remain after leaving the camera view.

  • Swept contactContinuous collision closes gaps between fast movement samples.
  • Sparse storageTrail memory exists only for grass touched by the player or a wandering ball.
  • Geometry responsePressed blades change position, direction, normals, and distant surface relief.
  • Timed recoveryGrass returns to its original shape before the system releases its stored trail data.

Trail uploads prioritize the nearest contact and use a fixed per-frame limit to protect the browser frame budget.

04 · Volumetric clouds and lighting

Raymarched clouds, projected shadows, and shared lighting stay consistent from every view.

I replaced flat cloud cards with bounded 3D volumes. Up to 64 clouds render through one procedural draw, while a compute-generated shadow field moves their shade across grass, terrain, balls, and meadow effects.

  • 3D volumeRaymarched density preserves cloud form and parallax as the camera moves.
  • Single drawA compact instance buffer renders the complete cloud field in one procedural submission.
  • Projected shadowsA GPU-generated field applies cloud shade to every world material.
  • Shared sunClouds, terrain, grass, sky, atmosphere, and actors use the same directional light.

A cloud disappeared at the centre of the camera orbit because of a signed projection error. Correcting the coordinate conversion fixed the view-dependent failure.

05 · WebGPU release

The browser build retains the complete visual system and meets its measured performance targets.

WebGPU changed the costs of managed code, first-use pipelines, memory growth, frame presentation, and GPU submissions. I built dedicated browser rendering, pacing, memory, and scheduling profiles while keeping the native cloud path and every defining scene feature.

  • Platform profilesDesktop and browser builds use separate renderers, pacing rules, memory settings, and schedules.
  • First-use warmupThe production scene prepares shaders, buffers, terrain, collision, and pools before control begins.
  • Frame budgetsStreaming, uploads, collision, particles, and diagnostics each have explicit limits.
  • Browser benchmarksAn automated harness measures workload, cadence, memory, errors, and repeatable scenarios.

The full-resolution native cloud path met the stress target, so I kept it. A lower-resolution reconstruction would have introduced ghosting without solving a measured bottleneck.

01 · Runtime conversion

The original map tool depended on Unity editor APIs.

The external map tool was a roughly 5,000-line Unity editor window. Undo, asset saving, scene changes, generated mesh assets, and direct project references all used editor-only systems that cannot run in a player or browser build.

I kept the established map rules and procedural generator, then replaced the surrounding editor infrastructure with runtime systems.

  • Portable documentMaps store stable tile, theme, and enemy IDs instead of Unity object references.
  • Runtime undoDrawing gestures and setting changes become bounded, reversible transactions.
  • Shared validationEditing and generation enforce the same legal map rules.
  • Resource ownershipThe runtime releases generated geometry, materials, and navigation before rebuilding.

02 · Runtime map authoring

The workshop combines cave layout, gameplay placement, validation, and build status.

The map stores cave shape, gameplay markers, and wall-mounted functions as separate layers. I designed the canvas to show the active tool, legal placement, topology, selected settings, warnings, and build readiness while editing.

  • Layered editingCave shape, gameplay objects, and wall functions remain independently editable.
  • Continuous gesturesFast drags fill skipped cells and commit as one undo step.
  • Topology rulesEvery tool preserves one player start, connected finish zones, attached pits, and configured encounter groups.
  • Clear validationErrors identify affected cells, while warnings remain visible without blocking a valid build.

4,096 cells in one custom UI mesh. The 64 × 64 canvas batches its symbols, outlines, previews, and validation feedback instead of creating thousands of interface objects.

03 · Runtime generation

Build and Play turns the authored map into the complete combat level.

  1. ValidateCheck a stable copy of the map before generation begins.
  2. ShapeGenerate floors, curved walls, a roof, pits, and repeatable seeded detail.
  3. PlaceAdd the player start, enemies, finish, healing pools, wind hazards, and guide lamps.
  4. CollideGenerate player-safe collision separately from the detailed cave meshes.
  5. NavigateBuild ground and flying enemy routes with runtime NavMesh.
  6. PlayConnect the existing combat systems and enter the generated cave.

Generation runs in measured stages and reports progress in the browser. The generated level uses the game’s movement, spells, enemies, pickups, hazards, death, completion, and reset systems. Players can return to the workshop, edit the same map, and rebuild it.

04 · Browser release

A dedicated WebGPU build supports runtime generation, persistence, and repeated playtesting.

Browser delivery required more than changing Unity’s target platform. I added capability checks, focus and pointer-lock handling, persistent map storage, resource cleanup, memory limits, compressed delivery, and build validation.

  • WebGPU preflightThe page checks secure context, desktop input, WebGPU, and a suitable adapter before downloading the game.
  • Clear support boundaryUnsupported setups receive an explanation instead of loading an unintended graphics fallback.
  • Browser sessionFocus, pointer lock, pause UI, storage sync, and rebuild cleanup have explicit runtime owners.
  • Release validationThe build checks renderer settings, memory, caching, Brotli headers, and required assets before shipping.
