Unity runtime tool · procedural level generation

Cave Map Workshop

I rebuilt an editor-only cave construction workflow as a product people can use at runtime. A designer can draw a layered 2D map, catch invalid topology before building, generate the complete 3D cave and navigation, and enter the existing spell-combat game without leaving the tool.

01 · The problem

Keep the mature map rules. Replace everything that could not ship.

The original map painter was an approximately 5,000-line Unity EditorWindow. It depended on editor Undo, AssetDatabase, prefab and mesh saving, scene mutation, and arbitrary project references. Those systems were useful in development, but none could become a browser product.

I separated the portable map data, editing transactions, validation, build coordination, persistence, UI, and generated-resource ownership into runtime-safe systems. The established tile rules and procedural MapBuilder stayed authoritative, so desktop and web use the same map logic instead of drifting into two implementations.

02 · Editor and authoring

A layered tool that protects intent while people draw.

Each cell can hold a cave base, a gameplay marker, and a Guide Lamp overlay. Brush, Rectangle, Region Fill, erase, resize, and function-tile edits all pass through the same transaction service and topology rules. A drag is one undo step; fast strokes rasterize between pointer events; top-layer erase preserves the cave beneath it.

  • One Player Start is normalized across the map.
  • The Finish Zone remains one edge-connected region.
  • Pit clusters stay attached to playable Floor.
  • Enemy encounter settings survive cluster merges and splits.
  • Structured validation reports errors, warnings, stable codes, and affected cells.

The 64 × 64 canvas is rendered as one custom UI mesh rather than 4,096 GameObjects. It batches tiles, symbols, topology outlines, previews, hover state, and validation overlays, keeping the browser authoring view practical without giving up precise feedback.

03 · Runtime generation

The authored plan becomes the real playable level.

  1. SnapshotClone and revalidate the versioned map document.
  2. GeometryBuild floor chunks, curved boundary walls, roof, pits, backdrops, and seeded stalactites.
  3. GameplayPlace spawn, encounter, finish, pool, wind, and lamp behavior from the authored layers.
  4. CollisionSeparate detailed visual and spell surfaces from clean player-safe pit collision.
  5. NavigationBake ground and flying NavMesh data after the current geometry exists.
  6. PlayBind gameplay references, reset into the generated map, and enter first-person combat.

Generation yields during large scans and between expensive stages so the browser can keep presenting honest progress. Every generated mesh, material, NavMesh object, and hierarchy belongs to a GeneratedMapLifetime; leaving play mode disposes that lifetime before another build begins. Shared project assets are never destroyed.

04 · WebGPU delivery

The web build is a target, not an export checkbox.

I built a dedicated Unity WebGPU renderer and quality path, then made the release validator reject any build that includes another graphics API. The browser page checks HTTPS, desktop input, navigator.gpu, and a high-performance adapter before downloading Unity. If WebGPU is unavailable, it stops with a useful compatibility message instead of silently switching renderers.

The release uses Brotli-compressed, hashed Unity artifacts; a 256 MiB WebAssembly heap can grow geometrically to 2048 MiB, and device pixel ratio is capped at 1.5. The host serves the compressed JavaScript, data, and WebAssembly with their required encoding and MIME headers so streaming compilation can work correctly.

The browser version targets desktop keyboard and mouse, requires a secure WebGPU-capable setup, and deliberately has no WebGL fallback. Runtime NavMesh baking remains a measured main-thread stage, so map dimensions, geometry, pits, objects, enemies, and estimated triangles are budgeted before generation begins.
